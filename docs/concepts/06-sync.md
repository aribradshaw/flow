# Sync

The server is the source of truth. Each environment's workspace is stored with a **revision** number, and the browser keeps an offline cache.

- `GET /api/workspace?env=<id>` returns `{rev, data}`. `PUT` with `{baseRev, data}` saves the workspace when `baseRev` is still current.
- If the workspace has moved on, the save gets `409` along with the newer copy. The client then merges per entity and field and retries. When both sides changed the same field, the local change wins. A deletion only applies to an entity the other side has not touched.
- DevOps cards are the exception: the board never sends its copy of them as edits. It keeps a list of the cards it changed itself (`cardEdits`: the fields it changed and what they were before, the cards it added and removed), and the server writes only those. Every other card stays as the server has it, so a copy that is out of date (a tab that slept, a browser that could not store its latest copy) never puts old descriptions, columns or due dates back on cards that an agent or another tab changed. When it was out of date on some cards, the answer includes `cardsKept: true` and the client reads the workspace again. An edit over a value the browser never saw (someone else changed that field meanwhile) gets `409` with `code: "card_conflict"`, the clashing cards and the newer copy; the browser shows it, keeps the user's edit and says so. A tab still running an older version of Flow that would change cards gets `428` (`reload_required`) and has to reload.
- A save that would drop most of a large workspace is refused with `422`, unless it is a deliberate load or replace.
- AgentFlow runners belong to the server: only `runners.report` changes them. A `PUT` keeps the runners as they last reported (their models and scheduled jobs), even when the saved copy is missing them or holds an older report, such as a tab still running an older version of Flow. The answer then includes `runnersKept: true`, and the client reads the workspace again.
- Card numbers only grow. A `PUT` with a lower `devops.nextNumber` keeps the server's and answers `countersKept: true`, so the client reads the workspace back.
- Every write first keeps the previous revision in the history. Postgres keeps it in `flygon_flow_workspace_history`; without Postgres it goes to `BACKUP_DIR/workspaces/history/`. The last 100 revisions are kept.
- A write that removes DevOps cards also records each card in `flygon_flow_card_deletes` (or `BACKUP_DIR/workspaces/deleted/`), in the same transaction, for 180 days (see Recently deleted on the DevOps board). A `PUT` may send `intent: {deleted: [card ids deleted on purpose], undo: true|false}` so the record says how each card left; other removed cards come back as `removedCards`.
- Open tabs pick up remote changes every 20 seconds, and offline edits upload when the connection comes back.

API writes go through the same revision check, so an agent's change and a human's edit never silently overwrite each other. An agent that reads a card and writes it back (for example, adding to its description) can send `ifUpdated` with the card's `updated` to `cards.update` or `cards.move`; if the card changed since, nothing is written and it gets `409 card_changed` with the current card.
